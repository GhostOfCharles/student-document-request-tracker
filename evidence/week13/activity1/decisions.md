# Activity 1 architecture and decision

This interpretation addresses the supplied AGENTS.md criteria and project Chapters 9 and 11. The course module itself was not found locally, so module-specific wording, rubric and oral/concept components are not independently verified.

Assumptions: one classroom registrar office, tens to hundreds of daily requests, a maintained local scheduler host, in-app delivery and synthetic files. The numbers are design assumptions rather than measured production traffic. The project maintainer owns code/configuration and worker operation; registrar staff own document and payment judgments. A student owns submission and receipt acknowledgement.

| Workflow | Alternatives and comparison | Selection and ownership |
| --- | --- | --- |
| Request status notification | Synchronous delivery inside the HTTP request offers immediate feedback and low deployment cost, but couples availability and latency to delivery, complicates retry after timeouts, and gives API workers delivery responsibility. An event outbox plus dedicated worker adds MySQL storage and operational staffing, but atomically preserves intent, keeps submission latency bounded and permits idempotent retries. Browser-only polling is feasible for discovery but cannot preserve a notification when the client closes. | API transaction queues intent; one worker creates recipient-scoped notifications. Maintainer owns worker; registrar owns event meaning. Up to one minute processing latency is acceptable for office requests. |
| Overdue and stalled work | Per-request timers can offer more precise deadlines, but correction pauses and service due-date changes require timer cancellation/replacement and many timer records. A periodic indexed scan handles current predicates and restart recovery uniformly, but has up to fifteen minutes detection latency and scan cost grows with volume. Manual spreadsheet review is feasible at small volume but depends on office staffing and consistent handling. | Fifteen-minute scan with episode keys and active-condition resolution. Registrar owns response to alerts; maintainer owns schedule and query behavior. This workload values reliable current-state detection over second-level latency. |
| Daily pending summary | Browser-generated reports on demand offer fresh data with little scheduler administration, but provide no reproducible unattended daily snapshot and depend on staff presence. A 17:00 local scheduler stores a consistent snapshot without a user being online; it needs timezone configuration, host availability and restart rules. An external cron task could call a protected command, but splits schedule ownership and duplicates deployment credentials. | Dedicated APScheduler local-time cron and unique summary_date, with audited current-day manual regeneration. Registrar interprets the report; maintainer owns scheduler. Actual generation time is retained after downtime. |

| Criterion | Notifications | Aging and escalation | Daily summary |
| --- | --- | --- | --- |
| Latency | One-minute worker interval; UI shows submission independently | Fifteen-minute detection interval | Fixed 17:00 Asia/Manila; delayed startup snapshot is explicit |
| Volume | One durable task per authorized recipient/event; backlog is visible | Current scan cost grows with requests; indexes support predicates | One date row; counts include six pending states |
| Reliability | Atomic outbox, lease, bounded retries, unique recipient/event | Repeated scans and unique episode keys prevent repeated active alerts | Consistent snapshot, serialized same-date writes, retained runs |
| Security | Session ownership and active-recipient authorization; IDs and safe parameters only | Staff-only alerts; correction/student-wait states excluded | Staff-only read/regenerate; historical dates cannot be regenerated |
| Staffing | Operator monitors failures; registrar acts on adverse cases | Registrar evaluates alerted work; no automated disciplinary decisions | Registrar interprets counts; operator handles failed schedule |
| Ownership | API owns intent, worker owns delivery, registrar owns workflow | Maintainer owns rule implementation, registrar owns intervention | Maintainer owns clock/run, registrar owns office meaning |

Trust boundaries are shown in docs/architecture/week13.md. The browser cannot invoke arbitrary code, choose recipients, rewrite historical evidence or set timers. Payment review, correction, rejection, preparation, handover and acknowledgement remain human decisions. Manual retry and resolution require staff authentication and a reason/note.

Adverse case: the worker host stops after persisting a claim but before delivery. The request remains committed and its notification intent remains in MySQL. After lease expiry, recovery records an interrupted attempt, preserves the attempt count and retries within the ceiling. A repeated event cannot create a second recipient/event notification. If the ceiling is exhausted, T09 directly exposes the permanent failure; visibility does not depend on a second worker notification succeeding.

Observed evidence: real MySQL tests exercise status delivery, repeated scans, local summaries, interruption recovery and failure routing; see verification/mysql-schema.json, logs/automation-tests.jsonl and activity2/observed-jobs.json. Browser captures establish that the Flutter client reads these records; they do not measure production latency or staff effectiveness.

Recommendation and limitations: keep one owned worker service and review T09 during office operation. In-app delivery is appropriate for the prototype; email/SMS and a production registrar integration are outside the slice. The host cannot execute while offline. A periodic scan trades precision for simple current-state recovery, and the current small-office implementation materializes records for summary calculation. Measured production sizing, independent instructor approval and actual user acceptance are not claimed.
