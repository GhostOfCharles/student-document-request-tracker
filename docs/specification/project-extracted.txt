Version 1.0  |  30 October 2026

Purpose and implementation baseline
This documentation defines the Student Document Request Tracker for students and registrar staff. It specifies the complete application scope, 25 planned screens, the versioned data model, API contracts, workflow controls, private evidence handling, automation and the development plan for Weeks 13 through 18.
The implementation baseline uses two roles, Student and Registrar Staff. Service management is an additional staff permission. Requests retain the service requirements in force at submission, corrections preserve earlier evidence, and every status change is validated by FastAPI. Week 13 prioritizes a working request lifecycle and demonstrable automation before the remaining interface refinements.
This is a design and implementation specification. Acceptance depends on executable migrations, integration tests and recorded demonstrations; the document does not certify a completed application.

Release boundaries
Password recovery A03 remains conditional until a verified recovery channel is implemented. Saved student drafts, real SMS or email delivery, payment processing, certificate generation, staff assignment, messaging, appeals and a separate administrator portal are excluded from the initial release. The planned A03 screen remains part of the 25 screen inventory without implying an active reset endpoint.

1 Scope and system architecture
Objectives and actors
Students select a document service, submit the required information and evidence, respond to correction instructions, track progress and acknowledge receipt. Registrar staff review requests, verify payment evidence where required, prepare documents, confirm physical release and monitor operational alerts. Staff with can_manage_services may configure and publish document services.
Selected technology stack
[TABLE]
Component | Responsibility
Flutter Web and Dart | Responsive browser interface, navigation, dynamic form widgets and authenticated API client
FastAPI and Pydantic | Authentication, authorization, validation, workflow transactions and OpenAPI contracts
MySQL with InnoDB | Relational records, constraints, durable job state and reporting snapshots
SQLAlchemy and PyMySQL | Database models, transactions and the MySQL connection driver
Alembic | Ordered and repeatable schema migrations
APScheduler 3.x | Time based triggers in one dedicated scheduler process
Private file storage | Evidence bytes stored outside public assets with database metadata
GitHub | Source control, reviewed changes and weekly assessment evidence
[/TABLE]

Component and transaction flow
Browser running Flutter Web
  | HTTPS and session cookie
Reverse proxy
  | /api/v1 -> FastAPI -> SQLAlchemy -> MySQL
  | static routes -> Flutter release build
FastAPI -> private evidence storage
Dedicated scheduler and worker -> MySQL automation jobs
Worker -> notifications and monitoring records

The HTTP application and the scheduler are separate processes. API transactions write business changes and durable automation jobs together. The worker consumes committed jobs and records attempts. File downloads pass through an authorized FastAPI route. MySQL and the private evidence directory are never exposed as public web resources.
Data ownership and historical integrity
Student ownership is derived from the authenticated session. Staff access is limited to the registrar workflow; there is no assignment subsystem. Published service versions and submitted revisions are immutable. Account and service deactivation preserve history. Ordinary operations do not physically delete historical requests or their evidence.
Operational time and money
All stored timestamps use UTC DATETIME(6) and all API timestamps use ISO 8601 UTC. The browser displays Asia/Manila time. Daily reporting dates and the 17:00 summary schedule use Asia/Manila. Processing estimates use calendar days. Payment amounts use DECIMAL(10,2) in MySQL and decimal strings in JSON; the initial currency is PHP.

The canonical visible label for submitted is Submitted. Pending Review is a staff dashboard aggregate label for submitted requests; it is not another database status. The optional draft status is reserved and has no initial release endpoint.
Permitted transitions
[TABLE]
From | To | Actor | Required conditions
New submission | Submitted | Student | Active service, current published version, valid complete requirements
Draft | Submitted | Student | Draft saving is implemented and all submission validation passes
Submitted | Under Review | Staff | Request is still submitted; no conflicting operation
Submitted | Cancelled | Student owner | Request has not entered staff processing
Under Review | Needs Correction | Staff | At least one specific correction issue and instructions
Under Review | Processing | Staff | Required evidence is valid; payment verified if applicable
Under Review | Rejected | Staff | Nonempty rejection reason
Under Review | Cancelled | Student owner | Cancellation occurs before another valid staff transition
Needs Correction | Under Review | Student owner | New complete revision passes validation and addresses requested corrections
Processing | Ready for Release | Staff | Staff confirms document preparation is complete
Ready for Release | Released | Staff | Staff confirms actual handover
Released | Completed | Student owner | Student explicitly acknowledges receipt
[/TABLE]

Completed, Rejected and Cancelled are terminal. There is no reopen endpoint. Cancellation is permitted only from Submitted or Under Review. It is unavailable in Needs Correction and all subsequent states. Rejection is allowed only while Under Review.
Action validation and atomicity
Submission validates an active service and its current published version, creates the request number and revision 1, writes history and audit records, and queues notification jobs in one transaction. No finalized request is created after validation failure.
Starting review requires Submitted. Requesting correction requires Under Review, meaningful instructions and at least one correction item belonging to the original service version. A request has at most one unresolved correction round.
Resubmission requires Needs Correction, the open correction round, the expected row version and a complete valid revision. Only identified fields or payment elements may change; unchanged values and file references are copied into the new immutable revision. The backend validates every listed correction and closes the round. Staff still judge the substantive quality of replacement evidence during review.
Approval requires Under Review, valid current requirements and no unresolved correction round. When payment is required, the latest payment review for the current revision must be verified. Approval advances directly to Processing and does not imply release.
Ready for Release requires Processing and staff confirmation that preparation is complete. Release requires Ready for Release and confirmation of actual handover. Only the student owner may acknowledge a Released request, which records Completed.
Each status action checks expected_row_version, validates current state, updates document_requests, increments row_version, appends status history and audit entries, and queues durable notifications in one database transaction. A stale value returns 409 VERSION_CONFLICT; the client reloads before presenting another action.
Timestamp rules
Set submitted_at and last_progress_at at first submission. Compute due_at as submitted_at plus processing_days calendar days. Beginning review, correction issue, correction receipt, approval, readiness and release update last_progress_at; opening a page or adding a note does not. Set released_at and released_by_user_id at handover, acknowledged_at at student acknowledgement, and closed_at for Completed, Rejected or Cancelled. Initial row_version is 1.
While Needs Correction is active, suspend staff delay alerts. On resubmission, extend due_at by resolved_at minus issued_at for that correction round. This calculation occurs once in the resubmission transaction. If a previous aging alert was open, resolve it on entering Needs Correction; a later overdue episode may create a new alert.

Enforcement rules
Every route authorizes the actor before returning protected data. Student access to another owner's request or file returns 404 RESOURCE_NOT_FOUND. Role restrictions return 403 PERMISSION_DENIED. Expired, revoked or inactive sessions return 401 AUTHENTICATION_REQUIRED. Student response models omit staff_only notes, internal_remarks, audit details and private storage metadata.
Ordinary staff may view version history and published configurations but cannot read or preview an editable draft through the manager routes. No web endpoint changes roles, grants service permissions or creates staff accounts. No user may edit submitted historical evidence or rewrite audit history.
5 Database definitions
Schema conventions
Use MySQL 8.0.16 or later with InnoDB, utf8mb4 and foreign key enforcement. Every id is BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY. Foreign key integer types match the referenced key. Columns are NOT NULL unless marked nullable. All timestamps are UTC DATETIME(6). No implicit database defaults are assumed unless stated; the application supplies required values in the same transaction.
Use ON DELETE RESTRICT and ON UPDATE RESTRICT for historical relationships. Draft child rows may be explicitly removed before publication; historical rows are retained. Controlled string values are enforced by validation and CHECK constraints where they concern a single row. Multi-table ownership and version membership are validated transactionally.
Initial defaults: users.can_manage_services=false, users.is_active=true, users.must_change_password=false for self registration, auth_sessions.remember_me=false, document_services.is_active=false until activation, document_requests.row_version=1 and current_revision_number=1, automation_jobs.attempt_count=0 and max_attempts=3. Count fields begin at zero; created_at and updated_at are supplied in UTC. Staff provisioning sets must_change_password=true.

All paths in this chapter are relative to /api/v1. Request and response bodies are JSON except multipart uploads and binary downloads. Reject unknown input properties. Credentials, roles, ownership, configured payment amounts and timestamps cannot be set by student payloads. Return 201 for new resources, 200 for ordinary success and successful replay, and 204 for deletion or logout without a body.
Each JSON response uses the resource shape defined below. Lists use {items, page, page_size, total}; page defaults to 1, page_size to 20 and is capped at 100. Newest-first ordering is created_at DESC, id DESC unless specified. History and revisions use ascending event or revision order. Dates accept YYYY-MM-DD; timestamps use UTC ISO 8601. Monetary values are strings.
Session and browser security contract
GET /auth/csrf returns a short-lived signed token and sets a binding cookie. Flutter sends X-CSRF-Token on all browser state-changing calls, including registration and login. Validate the signature, cookie binding and configured Origin before processing. Renew the binding on login. The token is not an authentication credential and is never placed in logs.
Login creates an opaque 256-bit random session, stores only its SHA-256 hash and sets the sdrt_session cookie with HttpOnly, Secure in production, SameSite=Lax and Path=/. Standard sessions expire after 8 hours; Remember Me sessions expire after 30 days. Expiry is absolute and server enforced. Local HTTP development may disable Secure only in the development configuration. Same-origin production routing is preferred; cross-origin development enables credentials only for explicit allowed origins.
Passwords use Argon2id through a maintained library. Accept 12-128 characters without silent truncation. Registration and password change require matching confirmation. Rate-limit login and registration at the server and return 429 with Retry-After. Invalid login returns 401 INVALID_CREDENTIALS with a neutral message. must_change_password restricts a temporary-password session to identity, CSRF, password change and logout endpoints until replacement succeeds.

Retry and idempotency behavior
Canonicalize the validated business payload after trimming normalized text, sorting answer and attachment arrays by requirement_id and resolving unchanged values. Exclude expected_row_version and client_submission_key from the hash. Store SHA-256 in the request or revision record. Before current-state validation on a retry, look up the authenticated owner and key; a matching hash returns the original immutable creation result even if the service or workflow later changed. A different hash returns 409. Another owner never receives the original resource.
The unique key and transaction handle concurrent duplicate calls. On a uniqueness collision, roll back and re-read the committed record before comparing. Initial replay returns the original submitted status and creation metadata; Flutter then fetches current details. Correction replay returns that revision's original result. Other workflow actions use optimistic concurrency: after a timeout, fetch current state rather than blindly replaying the action.

Draft editing and publication
Create a stable service identity and one editable draft. Draft edits may remove fields or incompatible settings because no submitted request depends on them. Preview uses the same Flutter widgets as the student form with uploads and submission disabled. Publication validates the full configuration, freezes it and updates the service current pointer in one transaction. A subsequent edit clones a new version, including new requirement and option IDs.
A student opening an older version must reload if the current publication changes before initial submission; return 409 SERVICE_VERSION_CHANGED. After successful submission, all corrections and historical views remain pinned to that original version. Service deactivation does not invalidate existing requests.

Exact limits are 5,242,880 bytes per file, 26,214,400 bytes combined and 10 file references per revision including the payment receipt. Each file field and the receipt are separate slots; a single file ID cannot fill multiple slots within one revision. Unchanged file references may be reused across revisions of the same request. A service may tighten these limits but never raise them.
Validation and private storage
Stream uploads with a hard byte limit; reject empty files. Check the extension, declared MIME, signature and decoded structure. Accept only JPEG, PNG and unencrypted PDF. Reject corrupt files, archives, executables and scripts. Apply image pixel and decompression limits, bounded PDF parsing and inspection timeouts. Sanitize the display filename to at most 128 characters and generate an independent random storage key.
Use FastAPI UploadFile for multipart handling. The upload and private-storage controls follow the FastAPI request-file documentation and OWASP file-upload guidance listed in Chapter 15. Validation is not a guarantee against malware. Classroom demonstrations use controlled non-sensitive evidence; public use of real documents requires an approved scanning and retention policy.
Lifecycle and access
Upload into private temporary storage, complete validation, then create stored_files with storage_status=staging, verified_at and a 24-hour staging_expires_at. On request submission, lock each selected file record, validate ownership and limits, link the revision and set ready. The bytes may remain at the same private storage key; a database status change commits the evidence without copying it.
Students may view their staged uploads and evidence attached to their own requests. Staff may view submitted evidence through the registrar workflow, including historical revisions and payment receipts. Staff cannot browse another user's unsubmitted staging files. Anonymous users and unrelated students receive no file data. Downloads validate both ordinary attachment links and the separate payment receipt link.
Use authenticated streaming, safe Content-Disposition, a verified MIME, private no-store caching and nosniff. Never reveal filesystem paths or issue permanent public URLs. Render authorized preview content in an isolated viewer; offer download when inline preview is unavailable.
Replacement and cleanup
Replacement creates a new stored file and a new immutable request revision. Preserve the old file and prior linkage. Reuse only unchanged evidence from the same request, or a staging file owned by the current student. A ready file from an unrelated request cannot be silently attached to a new request.
The daily 02:00 Asia/Manila cleanup locks expired staging records and checks request_attachments and request_revisions.payment_receipt_file_id immediately before deletion. It never removes referenced evidence. Mark unreferenced expired records removed and delete their bytes with a retryable cleanup step. A submission using a removed file fails validation. Clean partial upload files only after a 24-hour safety window, and reconcile metadata against private bytes after crashes.
Initial prototype retention preserves all submitted evidence and history for the assessment period. Ordinary UI deletion is unavailable. Before use beyond the controlled prototype, the institution must approve a retention period and deletion process covering live records, private files and backups.

[TABLE]

Run exactly one APScheduler 3.x scheduler with explicit job IDs, coalesce=true and max_instances=1 for each trigger. APScheduler triggers are re-registered at startup; the 23-table application model stores business work and execution history, not an APScheduler SQL job store. Do not start a scheduler in each FastAPI web worker.
Aging and stalled request rules
Aging applies when now >= due_at and status is Submitted, Under Review, Processing or Ready for Release. Escalate if now >= due_at + 48 hours in those states, or when Submitted or Under Review has no meaningful progress for 72 hours. Needs Correction, Released and terminal states are excluded from staff delay scans.
Resolve alerts when their predicate becomes false. Use event keys built from request ID, alert type and episode anchor: due_at for overdue episodes and last_progress_at for no-progress episodes. When both escalation predicates are true, create one escalation for that episode and include both reasons in safe job metadata. Count distinct requests rather than alert rows in summary metrics. Escalation creates an in-app staff alert without introducing supervisors or assignment logic.
Daily summary semantics
At 17:00 Asia/Manila, calculate all counts in a consistent database snapshot. Store one row for the local summary_date with generated_at. pending_total includes the six nonterminal submitted states, including Released and Needs Correction. completed_today_count, rejected_today_count and cancelled_today_count use closed_at in the local-midnight-to-generation interval converted to UTC. The 17:00 snapshot is not a midnight-to-midnight report.
Staff can regenerate only the current local date. Serialize generation by the unique summary_date and record the new run and audit event. Historical snapshots remain unchanged. If no summary exists, report SUMMARY_NOT_GENERATED instead of inventing counts.
Worker claims and retries
Each minute, claim eligible pending jobs transactionally using a row lock and a 120-second lease. Increment attempt_count and insert a running attempt with the same attempt number before execution. Workers renew the lease every 30 seconds during long work. All completion updates verify the worker identifier and lease before committing. A stale worker cannot finalize a reclaimed job.
[TABLE]
Attempt | Timing after preceding failure | Outcome
1 | Initial execution | Success completes the job; a permanent error stops immediately
2 | 1 minute after transient failure 1 | Retry the same idempotent operation
3 | 5 minutes after transient failure 2 | Final automatic attempt; failure becomes failed_permanently
[/TABLE]

Transient failures include temporary database connectivity, bounded worker timeouts and temporary dependency unavailability. Permanent failures include unsupported job types, invalid configuration and recipients who are not authorized to receive the event. Database outage may prevent recording the immediate failure; durable prior job state and the expired lease provide restart recovery.
On restart, mark an expired running attempt interrupted, release the claim and requeue the job if the retry budget remains. After the budget is exhausted, set failed_permanently. Preserve every attempt. Finalization writes the notification, its unique recipient/event key, the succeeded attempt and job status in the same transaction. A uniqueness conflict for an already-delivered event is an idempotent success.
Manual recovery and permanent failures
T09 shows safe error codes, attempt times, outcomes and unresolved failures. Staff may retry only an allowlisted idempotent operation after entering a reason. Lock the failed job; extend max_attempts by three and retain attempt_count and all previous attempts. Permit at most two manual retry cycles, for a maximum of nine total attempts. Each cycle is audited; a running or completed job cannot be retried.
Manual resolution requires a nonempty resolution_note and records resolved_by_user_id and resolved_at with status resolved_manually. It records that staff addressed the failure; it does not assert that the original action succeeded. A permanently failed notification must be surfaced through the monitoring query directly so failure visibility does not depend on another successful notification job. Failure-alert delivery cannot recursively create unlimited failure alerts.
Offline recovery and missed schedules
At startup, immediately process persisted pending work, recover expired leases and execute one aging, escalation and cleanup scan. These scans evaluate current state and do not reproduce every missed interval. If the current local date has reached 17:00 and lacks a summary, generate a delayed current-state snapshot and retain its actual generated_at. Do not reconstruct missing past-day snapshots from present data. Before 17:00, resume the normal current-day schedule.
The scheduler cannot run while its host is offline. Continuous deployment therefore requires a persistent scheduler/worker service. A self-test job may inject a first-attempt transient error in a test environment; a separate invalid test task demonstrates permanent failure. Production does not expose failure injection endpoints.

Deployment target and selection criteria
A small persistent Linux VPS is the reference topology: HTTPS reverse proxy, Flutter static build, FastAPI application service, MySQL, private storage and one scheduler/worker service. Hostinger VPS is a candidate rather than a selected purchase. Other VPS or managed providers qualify only if they support the selected Python runtime, persistent processes, private durable storage and MySQL access. Provider pricing, promotions and runtime support are evaluated at Week 16; they are not fixed project assumptions.
Release procedure
Build and test the release from a tagged commit. Record dependency versions, configuration names and required schema revisions.
Create a least-privileged database account and persistent private storage owned by the service account. Supply runtime secrets outside source control.
Back up MySQL and evidence consistently, stop writes for incompatible migration changes, apply Alembic migrations and start the API service.
Serve the Flutter release build through the reverse proxy. Route /api/v1 to FastAPI and configure SPA route fallback only for frontend routes. An unknown API path must remain an API 404.
Enable HTTPS, certificate renewal, explicit origins and secure session cookies. Limit public ports to the necessary web endpoints; keep MySQL on a private interface.
Start the dedicated scheduler/worker under a service supervisor with restart-on-failure. Ensure only one scheduler runs across all application instances.
Run release smoke tests: both roles, dynamic service, submission, secure file access, review, correction, payment, handover, acknowledgement, notifications and monitoring.
Record the deployment result, release commit, schema revision and actual automation timestamps in Week 16 evidence.
Backup and recovery
For the classroom deployment, perform a daily encrypted database and private-file backup with a documented seven-day rolling retention. Restrict backup access and keep at least one copy off the application host. This operational default is separate from institutional retention for real student documents. Test restoration before release and after a material schema or storage change.
Restore MySQL and the matching evidence set together into an isolated environment. Verify file hashes, attachment references, current service pointers, pending jobs and login access. Resume the scheduler only after database and storage checks pass. The prototype recovery objective is restoration from the latest daily backup; actual recovery duration is measured during rehearsal rather than assumed.
Rollback and monitoring
Retain the preceding compatible application build and its configuration. Prefer a forward corrective migration; do not downgrade a schema destructively after new evidence or requests have been written. For an incompatible rollback, stop writes and restore the paired database/file backup with documented data-loss implications.
Monitor API availability, database connections, private storage capacity, backup success, last scheduler runs, overdue pending jobs and permanent failures. Structured logs contain trace_id, event type, safe entity IDs, duration and result. They exclude passwords, session or CSRF tokens, raw receipts and full sensitive answer sets. Check monitoring queries directly when notification delivery itself fails.
Handover package
Handover includes the release tag, configuration inventory, migration history, acceptance results and deployment and restore procedures. Transfer credentials securely. Verify the maintainer can restart services, restore backups and review failures independently.

Consolidated implementation decisions
The 23-table count includes all permanent business entities. The conditional password reset table is not counted as core. No extra payment transaction, admin, messaging or staff assignment table is introduced.
Initial and corrected submission keys are integrated into their table definitions. Canonical payload hashes make different-payload key reuse enforceable. Draft service row_version supports concurrent editing without overwriting another manager's change.
Job statuses include resolved_manually; attempt outcomes include running and interrupted. Retry Pending remains a display label rather than an extra stored status. Manual retry preserves cumulative attempts and audit evidence.
Cancellation is limited to Submitted and Under Review, including when earlier general descriptions say before processing. Students cannot cancel Needs Correction under this baseline.
Published configurations remain pinned for historical requests. New initial submissions use the current publication; correction submissions keep the original version even if the service is inactive or republished.
Payment evidence outcomes and document request statuses are independent. The latest review is revision-specific, and corrected submissions require fresh payment review before approval.
Aging excludes student correction waits and Released requests. pending_total still includes both because they are nonterminal. Daily summaries use a 17:00 local snapshot and actual generation time.
The staff service detail endpoint supplies published version history; draft content remains service-manager-only. Profile avatar upload, optional student drafts and password recovery have no active initial-release API.
The scheduler uses registered time triggers with durable business jobs in MySQL. Restart scans recover current conditions without fabricating missed historical snapshots.
